# AI Assistant — Detailed Changelog

Full history of how the AI Assistant chat feature (`src/methods/assistant.js`, `cf-worker/index.js` `handleChat`) got to its current state — root causes, abandoned approaches, live-test verification. Not auto-loaded into every Claude Code session; see the condensed "AI Assistant" section in `CLAUDE.md` for the current-state facts that matter day to day. Read this file when you need the *why* behind a specific piece of the current design, or before changing something this history already explored and rejected.

---

## Model config: thinking, effort, max_tokens (2026-07-24)

Started at `thinking: {type: 'disabled'}` + `max_tokens: 1500` because an *omitted* `thinking` param runs adaptive by default on `claude-sonnet-5` (unlike `sonnet-4-6`, which defaulted to no thinking) and was silently eating most of the 1500-token cap, truncating replies ~90% of the time — disabling it explicitly fixed that and `max_tokens` was raised to 2500 for headroom. But once the lineup-advice template got precision-heavy — cross-checking three attribute columns for set-piece takers, comparing fitness numbers, computing GW staleness — thinking-disabled started producing a *different* failure mode: self-contradictory sub-timing values and visible "actually check: Saka 70/80/85, Eze..." scratch-work leaking into the reply, because the verification work had nowhere to happen except inline in the visible text.

**Re-enabling adaptive thinking fixed this**, verified directly: same prompt, thinking off → wrong/inconsistent set-piece picks and leaked reasoning; thinking on → correct picks every time ("highest Cor attribute in the XI at 88"), clean output, no leakage. `budget_tokens` is fully removed on `claude-sonnet-5` (400s) — `{type: 'adaptive'}` is the only on-mode; depth is tuned via `effort`, not a token budget. `effort: 'medium'` was tested too (with thinking still disabled, before this fix) and gave no measurable improvement over `low`, so `low` stayed — that test is why thinking was suspected as the actual variable once precision issues persisted at `medium`. `max_tokens` raised 2500→6500 for adaptive thinking's own token spend: a real test used ~2200-2500 thinking tokens + ~1550-1800 visible-reply tokens (~4000 total) for a full 6-section reply — 6500 leaves margin without being wasteful. This does raise real per-message cost (thinking tokens are billed); re-test `max_tokens`/whether thinking is still needed if `buildChatContext()` changes significantly.

## Structured outputs for lineup-vs-opponent replies (2026-07-24)

Even with adaptive thinking, the free-text 6-section template kept producing small mechanical errors — self-contradictory sub timing, occasionally the corner-tactics section still missing. Rather than continuing to prompt-engineer free text, "how should I line up against X" questions now get JSON-schema-constrained output instead. `_isLineupVsOpponentQuestion(text)` in `assistant.js` is a cheap client-side regex heuristic (lineup-intent phrase + "against"/"vs" + a real club name from `allPlayers`) — not an LLM call — that sets `lineupMode: true` on the `/_chat` POST only for this specific question type; every other question (transfers, scouting, general squad talk) is unaffected. `cf-worker/index.js` then adds `output_config.format: {type:'json_schema', schema: LINEUP_SCHEMA}` to the Anthropic request, so e.g. a sub's timing field is a real `anyOf` union matching the game's actual window/condition combos (scraped from `submit-team-v2`'s own JS — only the Half-time window offers "if losing") — a malformed pairing is now structurally impossible to generate, not just discouraged by wording. The frontend needed zero changes: `formatLineupReply()` in the worker converts the parsed JSON into the exact same markdown look a free-text reply would have produced, before it's ever returned as `{reply: "..."}` — same response contract as always.

Real pitfalls hit building this, in order: (1) `minItems`/`maxItems` above 0/1 are rejected by Claude's structured-outputs schema subset ("complex array constraints not supported") — the "exactly 11 lineup slots / exactly 5 subs" counts are prompt-level `description` text only, not schema-enforced, since item *shape* (where the real bugs were) doesn't need it; (2) the original schema required ~13 separate free-text reasoning fields (one per instruction, one per sub) and at `effort:'low'` several came back as the literal string `"placeholder"` — schema-valid, content-garbage; (3) tried `effort:'medium'` to fix it — thinking ballooned to ~7950 of an 8500-token budget and truncated the JSON entirely, too expensive to be the fix; (4) consolidating to one reasoning paragraph per section fixed it on the first test, then it recurred on the second — the failure is genuinely probabilistic, not deterministic, and always starts at the same point in property-declaration order regardless of remaining token budget (fields before that point are reliably real content, fields after are placeholder). Final fix, verified clean across 3 consecutive live tests: reordered schema properties so every mechanically-important field (lineup, instructions enums, subs, set pieces, corner enums) is declared *before* any free-text reasoning field, made every reasoning/overview field optional (omitted from its object's `required`, so a degraded generation can legitimately skip it instead of filling it with filler that still passes validation), and added `cleanText()` in the worker as a last-line-of-defense regex scrub (`/^\s*(placeholder|tbd|n\/?a|todo|xxx?)\s*\.?\s*$/i`) that blanks any field matching common LLM filler-text patterns before formatting.

Test via: mock `this`, call `buildChatContext()`, POST with `lineupMode: true`/`false`; for the true case, grep the reply for stray `placeholder`/`?` occurrences and count lineup slots (`grep -cE '^(GK|RB|CB|LB|DM|RW|AM|LW|CF):'`) and sub lines (`grep -c "IN for"`) to confirm exactly 11/5 — run at least 2-3 times given the probabilistic failure mode, a single clean run doesn't prove the fix.

## Context content additions (2026-07-24)

- `buildChatContext()` summarizes the already-loaded squad, budget, and top-rated transfer targets (no extra API calls). Squad line includes `p.fitnessPct` so the assistant can factor fitness into lineup suggestions.
- **Pricing**: raw `Value` is unreliable (scarce supply/high demand inflates real fees above it) — uses `trueVal(p)`/`trueValSrc(p)` (`espionageMethods`, `computeTrueValues()` in `src/methods/espionage.js`) instead: last real transfer fee > active listing ask > recent negotiation signal > rating-scaled formula fallback. Context also includes recent real completed transfers and the current transfer list with asking prices, so the assistant has concrete comps instead of guessing.
- **Lineup-suggestion columns**: `AltPosFit` (each player's `calcGameRating()` score at every other compatible position — same formula as `Rating`, evaluated at a different slot, so an inflated nominal-position rating from one shared attribute like Stamina shows its true alternate score alongside it), `Ldr/Ment/Exp` (`Leadership`/`Mentality`/`Experience`, for captain suggestions — Leadership first since it should dominate the pick), `FK/Pen/Cor` (`Free kicks`/`Penalties`/`Corners` — real dedicated API attributes that existed on every player object but weren't used anywhere before this). Guidance line tells the assistant not to default to listed Position/Rating alone, and that the game allows 5 subs (not 3).
- **Game mechanics reference**: static block of fixed game rules, verified straight from the live `/submit-team-v2` JS bundle (not historical submission data, which carries stale option values from before game updates). Formation tiers by Analytics Dept level; the 6 match-instruction dropdowns and exact options (Mentality has 5 values incl. Very Attacking/Very Defensive; Pressing Intensity is only 4 options despite older submissions containing now-retired values like Aggressive/Passive/Mixed); penalty/free-kick "instructions" are just a taker assignment (only corners have real tuning); 5 subs per match, each with a Plan + Timing trigger (only Half-time offers "if losing"). Reports MY_CLUB's live Analytics Dept level via `this.clubFacData?.levels?.analytics` when available.

## Sub Plan semantics bug (2026-07-24)

A sub's Plan is a mentality override, not a player description — verified straight from the game's own JS: `/submit-team-v2`'s form literally labels the field "Instruction" (not "Plan"), using the same 5-value mentality scale as the top-level Mentality setting. Per the owner (who observes actual match outcomes, which the client-side JS can't reveal): the value takes effect from that substitution onward and **persists as the new baseline mentality** until a later sub sets a different one — it isn't a per-player label. A real reply had all 3 "any situation" subs default to "Balanced" while the match started on "Attacking" — since only the first of those three subs was actually a change, the net effect was a silent, unintended downgrade to Balanced for most of the second half. Fixed in `buildChatContext()`'s game-mechanics reference, the free-text template, and the `subs` schema description: the 3 "any situation" subs should carry the SAME Plan as the match's starting Mentality by default, and only the "if winning"/"if not winning" subs should actually change it.

## CB/FB/DM candidate comparison unreliable (2026-07-24)

A real reply moved Schouten (DM) to CB at a rating of 78.5, *lower* than his own DM rating of 82.0 — a straight downgrade with no offsetting benefit. Root cause looked like sequential, non-holistic decision-making — the model settled on a flexible player for one slot without re-checking whether that left a worse combination elsewhere. Same reply also started two lower-rated fit DMs over a higher-rated one with no stated reason. Fixed: guidance now requires listing every viable candidate (natural + flexible) for each contested CB/FB/DM slot before finalizing, forbids repositioning to a slot rated *lower* than the player's own natural position, and requires a stated reason whenever a higher-rated fit natural candidate is left unused. Verified clean across 2 live tests.

## Structured lineup-vs-opponent reply template + "lost in the middle" fix (2026-07-24)

When there's opponent submission data, `buildChatContext()` prepends a 6-section reply template (deliberately the *first* substantive content in the prompt, right after the club/budget header): opponent breakdown (with staleness check) → flat one-line-per-slot lineup with captain marked `(C)` → 6 match instructions → exactly 5 subs → set-piece takers → 4-line corner-tactics block. A checklist reminder repeats at the very end of the context.

**Position matters more than wording**: an earlier version placed the identical instructions mid-context (after squad/targets/deals/transfer-list, before the opponent-tactics table) and it failed 6/6 live tests — the model consistently merged/omitted the corner-tactics section and reverted to grouped prose, regardless of wording strength, `max_tokens` headroom, or `effort` level. Moving the same instructions to the start (primacy) plus a tail reminder (recency) — the standard mitigation for "lost in the middle" in long contexts — fixed it to 100% compliance across repeated tests. Trimmed `targets`/`recentDeals` slices (40→25, 30→20) at the same time to reduce competing content.

Test via direct `/_chat` POSTs with real fetched squad/submission data — far more reliable than driving the actual browser, since local `vite preview` has no proxy for `/sf-cache/*` relative-path calls, so opponent-tactics data never loads in a local headless test.

## Matchup-driven reasoning fixes (2026-07-24)

The template above got tightened after real testing showed generic tactical filler and, worse, a nonsensical swap of two players' positions with no stated reason. Fixes: (1) a primer line requires working out concrete personnel matchups (e.g. "my RW vs their LB") and letting that drive the whole reply; (2) Section 1 requires naming at least one specific matchup rather than team-level generalities; (3) lineup lines show the rating at whichever slot the player is actually playing, and repositioning off natural position requires citing both numbers; (4) instructions/subs each require a matchup-specific reason, not boilerplate; (5) corner Delivery has a fixed target zone baked into the game (Inswinger→far post, Outswinger→near post, Driven→penalty spot, Short Corner→pulls a defender wide) — not an independent choice.

## GW staleness math, fitness/rotation judgment, holistic assignment (2026-07-24)

- **GW staleness computed deterministically**, not left to the model. First attempt used `GAME_START + asOfWeek * WEEK_MS` (mirroring `estCurrentWeek()` in `utils.js`) — wrong, caught by testing: this league's gameweeks don't tick a strict real-time 7-day cadence, so a submission made in the same instant as the request got flagged "14 days in the future." Rewritten to anchor on `new Date()` / the real calendar Saturday-Friday week (later refined further, see Phase 9 below).
- Reasoning paragraph moved before the flat lineup list; lineup lines carry fitness; the literal string "AltPosFit" banned from replies.
- Holistic-assignment guidance added for flexible attackers (AM/WF/CF) after a real test moved one player to a worse slot to accommodate another without checking the group's total rating.
- Set-piece takers required to be checked independently per attribute (Pen/FK/Cor) — a real test handed all three to one player who wasn't actually best at any of them. Post-fix testing showed the model self-correcting mid-reply, though not yet perfect on every check.
- **Fitness/rotation judgment**: a real test started a fatigued 82-rated player over a fresher 82.25-rated bench option — not even a real tradeoff, picked on reputation. Fixed: if a fresher alternative's rating is equal to or higher, start the fresher player; a small edge for the tired player alone isn't worth the risk. Verified directly, generalized correctly to a second unrelated case.
- **Holistic CB/FB/DM assignment / opportunity cost**: extended from the AM/WF/CF principle after the owner explained real preferences (a fringe DM can play FB freely; a first-choice DM generally shouldn't just because the numbers say so) — generalized as "would I actually play this out of position, or only in an emergency," not hardcoded to specific players. Verified across 2 live tests. This recurred and was tightened further in Phase 9 below.

## Opponent tactics source bug (2026-07-24)

`buildChatContext()` dumps every other club's most recent submission (can be a not-yet-played gameweek's plan, doubling as a predicted XI). Fixed to read `this.submissionsCache` directly instead of the separately-maintained `this.espionageSubmissions` snapshot, which is only (re)computed once during the bulk prewarm — reading the snapshot meant a club could be sitting right there in the live cache (e.g. from just browsing that club's Clubs-tab page) and the Assistant would still say "no data." `espionageSubmissions` itself is unchanged and still powers the Clubs-tab list badges. Also includes the last 8 of MY_CLUB's match results. There's no fixture/schedule endpoint anywhere in the app, so the assistant can't say who Arsenal plays *next* — only past results and clubs' latest tactics.

## Context truncation bug (2026-07-24)

`handleChat` truncates `body.context` before it reaches the model — separate from `MAX_CHAT_BODY_BYTES` (20MB whole-request limit). At full realistic scale (real squad + ~48-club opponent-tactics table + targets/deals/listings), `buildChatContext()` produces ~27-28k characters. The cap was 16,000 — the trailing ~40% of the prompt, including the entire opponent-tactics table, was silently cut off every time, so lineup-vs-opponent questions got "I don't have scouting data on X" even with the data fully loaded client-side. Raised to 120,000. Likely borderline-broken even before that day's Assistant additions pushed context over the old cap. Truncation is silent (no error) — re-verify context size against the cap if `buildChatContext()` grows significantly.

## Phase 9 fixes (2026-07-25) — from live-reply feedback

Five issues reported against a live Aston Villa lineup reply, all fixed and live-verified:

1. **GW window now 9pm-BST-anchored, not midnight-UTC-anchored** — per explicit correction ("we can extend the gw, say from saturday 9pm bst to saturday 9pm bst"), the window computation derives London's real UTC offset via `Intl`/`toLocaleString` diffing (tracks BST/GMT automatically) and anchors the Sat-Fri window to 9pm London-wall time on the most recent Saturday.
2. **Reasoning-before-list regression**: `formatLineupReply()` was rendering `lineup_reasoning` after the flat lineup list — opposite of the established free-text rule, introduced when the structured-output formatter was first built and never re-checked. Fixed.
3. **Set-piece ratings missing from structured output**: `LINEUP_SCHEMA`'s `set_pieces` had name fields only, no numbers — a real regression versus free-text mode. Added `penalty_rating`/`freekick_rating`/`corner_rating`.
4. **Fitness-comparison reasoning citing irrelevant players**: a live reply justified keeping a fatigued starter by citing an unrelated player's numbers. Fixed: any fitness/rotation comparison must be between the fatigued starter and the real candidate(s) for that specific slot, or state plainly no realistic fresher alternative exists.
5. **Zubimendi-to-FB opportunity-cost loophole, recurring a third time**: the Phase 8 guidance listed substantial-edge / strong-cover / emergency as three OR'd conditions, so "we have other good DMs" alone was enough to justify the move. Root-caused directly from a live reply's own words: *"with Schouten, Gravenberch and Lerma all fit and strong at DM, moving him out there costs us little cover."* Fixed by requiring squad depth AND rating edge as two SEPARATE requirements that must both hold, plus an explicit note to treat a large edge for a specialist holding/destroyer-type DM with extra skepticism (the formula can undersell his real defensive-midfield value while a flattering alternate-position number can come from just one or two shared physical attributes). Verified 3/3 clean live runs post-fix (previously 1/3 failed with the OR-based wording); one run showed the fix generalizing correctly — it moved Gravenberch (explicitly identified as squad depth) instead of Zubimendi.

## Structured-output reliability regression (2026-07-25) — same day as Phase 9

Reported live: an empty Substitutions section and blank/zero set-piece fields ("Penalty: ? (0 Pen)"). Live testing (5 real requests) confirmed 3/5 came back broken. Root cause was NOT token truncation — `stop_reason` was `end_turn` every time, output_tokens well under the 8500 cap — it was the model, at `effort:'low'`, sometimes returning schema-*valid* garbage: `subs: []` (nothing in the schema forbade an empty array) twice, and once genuinely corrupted trailing JSON that failed `JSON.parse` outright. The extra Section 2 guidance added earlier the same day (tightened CB/FB/DM rule, relevant-alternatives rule) is the likely trigger — more nuanced tradeoffs at a fixed low-effort budget made the "harder" fields (subs array, trailing free-text) more likely to get skipped or garbled.

Two-part fix: (1) **schema hardening** — `minItems:1` on the `lineup`/`subs` arrays and `minLength:1` on every player-name/slot/set-piece-name string, which structurally forbids the exact empty-array/blank-string patterns observed. Tried `minimum:1` on rating number fields too — rejected by the API outright ("For 'number' type, property 'minimum' is not supported", a live 400 caught immediately by testing), so a `0` rating relies on the runtime check instead. (2) **Server-side detect-and-retry** — `isLineupReplyBroken(parsed)` in `handleChat` checks the parsed response for the exact failure shapes seen and retries the entire Anthropic call once if broken or unparseable, before falling back to best-effort. Live-verified 5/5 clean post-fix, including 2 that were caught and self-healed by the retry — confirming the retry path itself works, not just that failures happened to stop occurring. Client-side timeout raised 110s→240s for `lineupMode` to cover a worst-case retry.

## Owner feedback round 3 on the real Liverpool test — reasoning depth + real opponent set-piece data (2026-07-29)

After round 2's fixes (real named Plans, two-part Section 1), the owner reviewed a real reply against the actual Liverpool matchup and gave six further, mostly-substantive notes, all addressed:

1. **Opponent breakdown wasn't reading individual Player Roles** — it said "both fullbacks push high" when only Kerkez (Overlapper) actually does; Timber is tagged Two-Way Full Back (more conservative), and Rice is Box-to-Box, not a true defensive Anchor. Root cause: the opponent-tactics table only ever listed XI player *names*, never their Role — the model was inferring generic behavior from mentality/formation alone because it genuinely couldn't see the per-player Role data, which exists in the submission (`xi[].role`) but was never exposed to it. Fixed by adding each player's Role in parens to the tactics table, plus explicit guidance that a Role is the real individual instruction and overrides generic mentality-based assumptions. Also asked: if an opponent has all 6 Plan B scenarios configured (reactive/scripted), is there an opportunity in that for us? Added guidance to actually answer this (anticipate their scripted reaction to a known trigger; a side that leans on scripts may be less fluid outside those 6 triggers) rather than just noting "well-drilled" as a passive observation.
2. **Lineup section wasn't explaining bench decisions or footedness** — asked why recognizable names (Hincapie, Schlotterbeck, Ødegaard in the reply reviewed) weren't starting, assumed fitness but wanted it stated; and pointed out Saka/Yılmaz, both given "Inside Forward", should be on *opposite* wings from each other based on which foot they favor (an inside forward cuts onto their stronger foot, so a left-footer plays right wing and vice versa). The game data does carry a real `PreferredFoot` attribute (`Left`/`Right`/`Either`, confirmed via a raw player object) that was never surfaced. Fixed: added a Foot column to the squad table, added explicit Inside-Forward-vs-Traditional-Winger foot-side guidance (opposite conventions — cut inside on strong foot vs. hug the line and cross with the outside foot), and made explicit-naming of every notable non-starter (any position, not just CB/FB/DM) a blanket Section 2 requirement instead of an implicit inference.
3. **Instructions treated "obvious" values as needing no reason** — "Balanced"/"Mixed"/"Medium" got no explanation while extreme values did. Fixed in both the free-text template and the structured schema's `instructions_reasoning` description: every one of the 6 fields needs its own real reason, moderate values included.
4. **Some sub lines still dropped their window** — a free-text formatting-discipline gap, not a data gap (the structured JSON schema already requires window/condition on every sub). Tightened Section 4's format instruction to the same rigor as Section 2's flat lineup list — one fixed 5-part format, no exceptions, no dropped fields.
5. **Asked whether set-piece takers are purely attribute-driven** — confirmed yes (already independently spot-checked against real Penalties/Free kicks/Corners attribute values in the round-2 entry above); no code change needed, just confirmed to the owner directly.
6. **Corner tactics ignored the opponent's own real corner-zone assignments** — Liverpool's actual submission carries a full `setPieces` object (`attackingCorner`/`defensiveCorner`, each with `delivery`/`scheme`/`press` plus a named player per zone — who they put at near post, far post, penalty spot, etc.) that was never read into context at all. Added it for any club actually named in the conversation (reusing the existing "mentioned club" enrichment pattern from the negotiation-support feature, rather than bloating the summary table for all ~48 cached clubs), and rewrote Section 6's guidance to require using it by name: identify their real attacking-corner aerial threats to mark on our defensive corner, and a real weakness in their defensive-corner zone assignments to target on our attacking corner.

Verified via 3 live free-text runs against the real Liverpool matchup, all clean, with every specific claim checked directly against the raw fetched submission data: Kerkez correctly called an Overlapper and Timber a Two-Way Full Back (not "both push high"); Rice correctly called Box-to-Box; Saka (confirmed left-footed) and Yılmaz (confirmed right-footed) correctly placed on opposite wings as Inside Forwards; and the corner-zone claims were all real — Szoboszlai genuinely at far post on Liverpool's defensive corner (an AM, correctly flagged as a mismatch), Van Dijk genuinely at the penalty spot and Isak genuinely at far post on their attacking corner (correctly flagged as their real threats), and Gordon genuinely their defensive-corner counter-runner.

lineupMode (structured) testing this round hit a *third* distinct ghost-item variant on the one clean completion obtained: `{slot:"CF-fix", player:"placeholder", rating:0, fitness_pct:0, role:"Poacher"}` as a 12th lineup entry. It slipped past both existing defenses from the previous two rounds — "CF-fix" is exactly 6 characters, matching the old `slot.length > 6` cutoff's boundary exactly (an off-by-one), and "placeholder" as a player *name* was never checked against `PLACEHOLDER_RE` (that regex only ever ran against free-text reasoning fields, never mechanical fields like `player`). Tightened `slot`'s length cap to `> 4` (every real slot code — GK/RB/LB/CB/DM/CM/WM/AM/WF/CF — is exactly 2 characters) and applied `PLACEHOLDER_RE` to the `player` field too, in both `isLineupReplyBroken()` and the render-time defensive filter. Not yet re-verified with a fresh clean lineupMode run (API load remained heavy for most of this session) — worth re-running once load normalizes.

## Player Roles + Plan B added to the game mechanics reference (2026-07-29)

Extended `buildChatContext()`'s "Game mechanics reference" block with the two mechanics documented in `CHANGELOG.md`'s "Clubs tab: Player Roles + Plan B" entry, which the reference didn't cover at all before this: Player Roles (`PLAYER_ROLES` in `src/constants.js`, gated by a player's own base position) and Plan B (`PLAN_B_SCENARIOS`, 6 fixed scenarios, fires at most once per match, no personnel changes) plus the owner-confirmed precedence rule ("a later sub instruction overrides an earlier Plan B, and vice versa: the most recent call wins"). Both lists are rendered into the reference dynamically from the constants (not hand-copied text), so they can't drift out of sync if the option lists ever change.

Per the CHANGELOG entry's own flagged ambiguity — the scenario→Mentality/Style mapping for a Plan B reaction isn't confirmed — the guidance explicitly forbids asserting a specific named Plan or exact instruction value for a Plan B reaction; the model may only name the scenario and a plausible plain-language tactical *direction* (e.g. "push for goals", "shut up shop and protect the lead").

Extended rather than added sections, per the existing "lost in the middle" lesson (see the entry below on the 6-section template): Role is folded onto each existing Section 2 lineup line ("SLOT: Player Name (rating, fitness%) — Role: Role Name") instead of a new section, and Plan B is a short block appended to the end of Section 4 (Substitutions) instead of a new Section 7. The tail checklist gained two corresponding line items (Role validity, Plan B block presence) rather than a new checklist section.

Same changes mirrored in the structured lineup-vs-opponent schema (`cf-worker/index.js`): `LINEUP_SCHEMA`'s `lineup` items gained a required `role` field (a flat 24-value enum across all base positions — the schema has no way to make an enum conditional on a sibling `slot`/`player` value, so which of the 24 is actually valid for that player's own base position stays prompt guidance, not schema-enforced); a new optional `plan_b` array (`{scenario, reaction}`, scenario from a 6-value enum, reaction free text) was added near the end of the mechanical fields, *not* in top-level `required` — consistent with the rest of the schema's rule that anything not confirmed/guaranteed stays optional so a degraded generation can omit it instead of filling it with invented specifics. `formatLineupReply()` renders the role inline on each lineup line and the Plan B block right after the subs list, before Set pieces — matching the free-text template's placement exactly.

Verified via the established methodology: a temporary `_scratch_live_test.mjs` built a real `buildChatContext()` context from real fetched data (`sf_players_v6` pulled directly off the deployed cache worker, ~1459 real players; a mocked-but-realistic Chelsea submission built from real Chelsea players sorted by rating, since the live `sf_submissions_all_v1` key wasn't populated at test time), then POSTed it straight to `https://sf-cache.ofersi15.workers.dev/_chat` (deployed after the schema/prompt changes via `wrangler deploy`, since the worker doesn't share the frontend's build — a first test round pre-deploy correctly showed zero Role/Plan B content, confirming the test harness was actually exercising the new code once deployed, not just always passing). 5/5 `lineupMode:true` runs and 3/3 free-text runs came back clean: every one of the 11 lineup lines carried a Role valid for that player's own base position (e.g. CF got Poacher/Complete Forward, DM got Deep-Lying Playmaker/Destroyer/Anchor/Box-to-Box, never a role from another position's list), the Plan B block appeared with scenario+direction only (no asserted named Plan or instruction value), and — the specific regression risk flagged for this change — the Corner tactics section (Section 6 / `corner_tactics`) was present and fully populated in all 8 runs, with Substitutions and Set pieces also intact every time.

## Real-matchup regression test: Arsenal away at Liverpool (2026-07-29)

Owner asked for a real test case rather than a synthetic one, using Liverpool's actual submission ahead of the weekend fixture (Arsenal, 2nd, away at Liverpool, 3rd — a real title-race match). `/api/submissions?club=X` turns out to need no auth (confirmed by reading `_fetchClubSubmissions()` in `clubs.js`, which calls it with a bare `fetch`, no headers) — fetched Liverpool's most recent submission directly (`submittedAt` inside the current GW window), which carries a real, fully-populated `xi[].role` set and all 6 `planBs` entries, plus the real Arsenal squad (`sf_players_v6` off the deployed cache worker). Built a mock `this` from this real data and POSTed straight to `/_chat`, exactly like the synthetic Chelsea test the previous entry used, but with a genuinely complex real matchup this time. This surfaced two real bugs the smaller synthetic test hadn't:

1. **Free-text replies truncating mid-Section-4** (3/5 runs cut off before Plan B/Set pieces/Corner tactics ever generated) — `wrangler tail` showed `stop_reason:"max_tokens"` with thinking alone consuming 4870 of the 6500-token budget (vs. ~2200-2500 in the original 2026-07-24 tuning), leaving too little room for the now-longer visible reply (per-line Role tag + Plan B block). One run even came back completely empty (thinking consumed the *entire* budget before any visible text started). Fixed: `max_tokens` for free-text raised 6500→8500 (now matching lineupMode), plus a server-side retry-once-on-completely-empty-reply safety net in `handleChat` (previously only lineupMode retried on a broken reply) and the client-side timeout for non-lineup messages raised to the same 240s lineupMode already used, since a retry can now double the wait.
2. **Structured lineupMode occasionally hallucinated a spurious 12th lineup entry** — 11 real starters plus `{slot:"?", player:"?", rating:0, fitness_pct:0, role:"Poacher"}`. `isLineupReplyBroken()` only checked for *too few* items (`< 9`), so this schema-valid garbage sailed through undetected and got rendered to the user. ## Root cause found and fixed for the recurring 524s: non-streaming call to a Cloudflare-fronted API (2026-07-30)

Owner asked to check status.claude.com directly rather than keep retrying blind. It showed a genuinely relevant clue: an "Elevated errors across many models" incident — explicitly including Sonnet 5, this app's model — was active for the entire span of the previous night's testing (confirmed resolved at 10:48 UTC, well after that session's last attempt at ~04:56 UTC) alongside a separate, still-open "Degraded performance on Claude Opus 4.8" incident (reported 13:43 UTC) that does not mention Sonnet 5. Retested at 14:01 UTC, past the resolution and unrelated to the new Opus-only incident — but still got a 524 on both attempts of a fresh lineupMode request, with server logs showing attempt 1 was a genuine content-quality miss (real `usage`, `stop_reason:"end_turn"`) and attempt 2 a real `error code: 524`. Since the one incident that plausibly explained last night's failures had already resolved hours earlier, this ruled out "still down" as the explanation for a *new* 524 and pointed at something in this app's own request shape instead.

**Root cause**: `handleChat`'s call to Anthropic (`callAnthropic()` in `cf-worker/index.js`) was non-streaming — `await fetch(...)` then blocking on the full response body. This request is inherently slow: adaptive thinking alone routinely burns 8,000-10,000+ tokens before any visible output starts, and even successful runs across this whole multi-day test history took 97-250+ seconds. `524` is specifically Cloudflare's own edge-to-origin timeout code, and `api.anthropic.com` is itself Cloudflare-fronted — with a non-streaming call, literally zero bytes flow back until the ENTIRE generation finishes server-side, so any fixed idle/total-duration timeout on an edge between us and Anthropic's inference backend kills a slow-but-perfectly-healthy generation with the exact same error code as a real outage. This explains why the failure rate looked "incident-shaped" (correlated with real Anthropic-side load) while also being persistent beyond any single incident's resolution: the app's own request complexity has grown across many past sessions (`max_tokens` alone: 2500→6500→8500→10000→16000, each raise chasing a truncation bug) without anyone weighing that the same growth increases *generation time*, and thus exposure to this exact failure mode.

**Fix**: added `stream: true` to the Anthropic request and wrote `readAnthropicStream()`, which consumes the SSE event stream (`message_start`/`content_block_start`/`content_block_delta`/`message_delta`/`message_stop`) and reconstructs the identical `{content, usage, stop_reason}` shape the non-streaming API returned — every existing content/usage/stop_reason reader, the retry loop, `isLineupReplyBroken()`, and `formatLineupReply()` needed zero changes as a result. The `!r.ok` branch (a real Anthropic API error, or a non-2xx gateway failure like a 524 error page) still reads the body as plain text/JSON exactly as before, since there's no stream to consume on an error status; a stream that starts fine (200 OK) but errors or drops mid-flight is caught separately and retried once, same budget as before.

**Verified live, immediately and decisively**: the very first post-deploy request (a fresh deploy landing only 11s before a test — Cloudflare's global propagation isn't instant — correctly still showed the OLD log message text, a useful confirmation the version boundary was real) hit a stale-version 524 as expected; every request from ~5 minutes after deploy onward has been clean at the HTTP level. Across 6 further live requests (2 free-text, 4 lineupMode) against the real Liverpool matchup: **zero further 524s** — a complete resolution of the specific failure that blocked 3 separate verification attempts spanning 6+ hours the previous session. One free-text run (159.6s) came back fully clean and was independently checked against every criterion this multi-session effort has been trying to verify: all 6 sections present, Section 4's 6 match-instruction lines each individually labeled with a real reason (including "Balanced"/"Medium"/"Mid-Block", not just extreme values — the actual originally-reported free-text bug), all 5 subs correctly matching position families with explicit "natural X-for-X" language in the model's own reasoning, and all 3 set-piece/corner claims checked against the real fetched Liverpool submission data (matched exactly). A second free-text run also came back fully clean (11/11 lineup lines).

## A separate, currently-active content-quality issue: lineupMode's structured JSON degrades more than free-text right now (2026-07-30)

The streaming fix above resolved the transport-level failure (524s) but exposed a second, distinct problem that had been masked by it: of 4 lineupMode (JSON-schema-constrained) requests post-fix, **all 4** came back with a degraded `lineup` and/or `subs` array — one with only 1 of 11 real lineup entries, one with a duplicated GK line (2 entries, one repeated), one with 9 of 11 entries plus a `subs` line reading literally `"none IN for none"`, each despite `stop_reason:"end_turn"` (not a token-budget truncation) and every OTHER field in the same response (`instructions`, `set_pieces`, `corner_tactics` — all flat objects, not arrays) rendering fully correct. Meanwhile the 2 free-text requests in the same window — asked for the exact same content, just as prose instead of schema-constrained JSON — both came back completely clean, including a correct 11/11 lineup list each time. This 0/4-vs-2/2 split, on identical underlying content requirements, points at the JSON-schema-constrained decoding path specifically being less reliable under current conditions than free generation — plausibly connected to the same broader model-serving issue behind the still-open "Degraded performance on Claude Opus 4.8" status page incident (unconfirmed whether Sonnet 5's structured-output path shares underlying infrastructure with Opus's, but the timing lines up), or a pre-existing fragility in schema-constrained array generation that just happened to surface repeatedly in this specific window — this exact "1 of 11" shape was seen exactly once before, right at the start of this whole multi-session saga, so it isn't unprecedented.

**Fix applied (UX only, not a root-cause fix)**: `formatLineupReply()` now counts the real (non-garbage-shaped) lineup entries after the existing ghost-item filter and, if under 11, appends "⚠️ Only N of 11 lineup slots came back this time — please ask again for a complete lineup." instead of silently rendering a 1-2 line list that looks like a rendering bug rather than a degraded reply. Verified live: the exact "9 of 11" case rendered the new warning correctly. This does not fix the underlying degradation — `isLineupReplyBroken()` already retries once on this exact failure shape, and 4/4 exhausted that budget — it only makes an unavoidable degraded reply honest about what happened instead of confusing.

**Not yet addressed, worth a decision**: since lineupMode's own JSON-schema constraint isn't actually buying additional count-enforcement over free-text right now (the schema's `minItems:1` ceiling means it never could enforce exactly 11 either — see the original "Structured outputs" entry above), and free-text is currently proving more reliable for the identical content, it may be worth temporarily preferring free-text over lineupMode (or raising `maxAttempts` beyond 2 specifically for lineupMode) until this stabilizes — not implemented without checking with the owner first, since it's a real behavior change to how "how should I line up against X" questions get answered, not a pure bug fix.

## General test methodology used throughout

Direct API tests: temporary Node scripts (`_scratch_*.mjs`, always deleted after use) that mock `this` with real fetched game data (squads via `/api/squads`, submissions via `/api/submissions?club=X&limit=50`, which returns `{items:[...]}` — not a bare array and no `gameweek` field, key by `submissionId` instead), call `buildChatContext.call(mockThis)` directly, then POST to the live deployed worker — far more reliable than browser-based testing (local `vite dev`/`vite preview` have no proxy for `/sf-cache/*`, so opponent-tactics data never loads locally). `wrangler tail -c wrangler.toml` from `cf-worker/` shows server-side `usage`/`stop_reason` logging, useful for distinguishing truncation from generation-quality failures. Given several failure modes here are probabilistic, not deterministic, a single clean test run never proves a fix — verify across 3-5 live runs minimum.
